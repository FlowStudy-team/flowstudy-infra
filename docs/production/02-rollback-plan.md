# 回滚计划

## 触发条件

- 登录、内容访问、提交判题或结果查询核心链路不可用。
- 数据库迁移导致数据错误或应用启动失败。
- RabbitMQ 消息格式不兼容导致任务堆积。
- Judge 沙箱异常导致大量系统错误。
- Nginx 配置导致前端或 API 无法访问。

## 应用版本回滚

当前未发现统一版本化部署机制。上线前必须明确每个仓库的构建产物、版本号、镜像 tag 或发布包路径。

## Docker 镜像回滚

当前未发现 Dockerfile 和有效 compose。补齐后要求：

- 镜像 tag 不使用 `latest` 作为唯一回滚依据。
- 记录上一个稳定版本 tag。
- 回滚只部署已验证镜像。

## 配置回滚

- 配置变更前保存当前生效配置。
- 密钥回滚必须人工确认，避免旧密钥恢复导致安全风险。
- 配置回滚后重启受影响服务并执行 smoke test。

## Nginx 回滚

`../../nginx/nginx.conf` 当前为本机 Windows 绝对路径配置。生产 Nginx 配置变更必须先执行：

```bash
nginx -t
```

回滚时恢复上一份已验证配置并 reload。

## 数据库迁移回滚原则

- 所有迁移前必须备份。
- 优先使用向前兼容迁移，避免应用和数据库必须同时切换。
- 不可逆变更不得自动执行，必须人工审批。
- 当前 migration 未提供 down 脚本，回滚依赖备份恢复或人工补偿 SQL。

## RabbitMQ 消息兼容性

- 消息新增字段应保持可选。
- 删除或重命名字段前必须同步 Core `JudgeSubmitMessage` 与 Judge `SubmissionMessage`。
- 当前 Core 和 Judge 使用默认 exchange + `submission_queue`，不应单方面改队列名。

## 不可逆数据库变更处理

- 删除列、删除表、批量更新业务数据必须先导出备份。
- 需要灰度双写/双读策略时，先写设计和验证计划。

## 回滚后验证

- 登录和 `/api/v1/users/me`
- 教程/博客/题目查询
- 代码运行/提交/结果查询
- RabbitMQ 队列堆积
- Judge 日志和 MySQL 状态
- AI 健康检查

## 回滚失败时的处理

- 冻结新的发布和自动重启策略。
- 保留日志、DB 备份、RabbitMQ 队列状态。
- 人工决定是否进入灾难恢复流程，参考 `04-disaster-recovery.md`。
